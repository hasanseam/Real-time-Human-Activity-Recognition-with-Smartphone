## Abstract

Human Activity Recognition (HAR) is a rapidly growing field at the intersection of pervasive computing and machine learning, with significant applications in healthcare, sports science, elderly care, and context-aware mobile systems. A fundamental prerequisite for building accurate HAR models is the availability of high-quality, labelled sensor datasets collected from real participants performing real activities.

This thesis presents the design, implementation, and evaluation of a configurable Android application for real-time smartphone-based sensor data collection, specifically intended for HAR research. The application — named **RealTimeHAR** — enables technical users and researchers to configure which device sensors to record, define custom activity labels and subject identifiers, collect multi-sensor data continuously in the background, visualize the recorded signals in real time, and export the resulting datasets as structured CSV files for downstream machine learning pipelines.

The application was developed in Java for the Android platform, following the Model-View-ViewModel (MVVM) architectural pattern to separate concerns between the data logic, business logic, and presentation layers. It leverages Android's foreground service mechanism to ensure continuous and uninterrupted data collection even when the app is not in active focus. Sensor configurations and activity definitions are persisted locally using an SQLite database, ensuring session continuity across restarts.

Usability and workload were evaluated using the System Usability Scale (SUS) and the NASA Task Load Index (NASA-TLX), two validated standardized instruments. Placeholder evaluation results are presented, alongside a discussion of the application's design decisions, limitations, and directions for future work.

**Keywords:** Human Activity Recognition, Android, Sensor Data Collection, MVVM, Smartphone, SUS, NASA-TLX, Machine Learning Dataset

## 1. Introduction

### 1.1 Motivation

The proliferation of smartphones as everyday devices has transformed them into powerful, always-carried sensing platforms. Modern smartphones are equipped with an array of onboard sensors — accelerometers, gyroscopes, magnetometers, barometers, and more — capable of capturing fine-grained motion and environmental data at configurable sampling frequencies. This makes smartphones uniquely suited for Human Activity Recognition (HAR), the automated classification of physical activities performed by a person, based on sensor signals.

HAR has a wide range of consequential applications. In healthcare, it enables passive monitoring of patients' mobility and recovery progress. In sports science, it supports performance analysis without the need for expensive laboratory equipment. For elderly care, it can detect falls, inactivity periods, or deviations from normal daily patterns and trigger alerts. In fitness and wellness applications, it underpins step counting, calorie estimation, and workout tracking features.

Despite the broad academic and commercial interest in HAR, a significant bottleneck in the research pipeline is the collection of high-quality, labelled, multi-participant training data. Existing publicly available datasets (e.g., UCI-HAR [1], PAMAP2 [2]) have been invaluable, but they are fixed, often collected with specific hardware, and may not generalize to novel device models, custom activity sets, or specific research populations. Researchers frequently need to collect their own datasets, yet no widely adopted open-source tool exists for configurable, researcher-facing smartphone data collection.

This gap motivates the present work.

### 1.2 Problem Statement

The central problem addressed in this thesis is:

> *How can a flexible, usable, and reliable Android application be designed and implemented to support researchers in collecting labelled, multi-sensor smartphone data for Human Activity Recognition tasks?*

Concretely, the application must:
- Allow researchers to select which sensors to record and at what sampling rate.
- Allow researchers to define and label the activities they wish to study (e.g., walking, running, sitting, standing).
- Support continuous data collection in the background without data loss.
- Provide real-time visual feedback of sensor signals during recording.
- Export structured, labelled CSV files suitable for direct use in machine learning pipelines.
- Be easy enough for non-developer researchers to operate without technical assistance.

### 1.3 Research Objectives

The specific objectives of this thesis are:

1. **Design** a researcher-centred Android application for configurable HAR data collection.
2. **Implement** the application using robust software engineering practices (MVVM architecture, foreground services, local persistence).
3. **Validate** the application through a structured user study using the SUS questionnaire and the NASA-TLX workload scale, targeting technical users and researchers.
4. **Discuss** the application's design decisions, limitations, and future extensibility.

### 1.4 Contributions

The main contributions of this thesis are:

- A fully functional, open-source Android application for multi-sensor HAR data collection, with configurable sensor selection, activity labelling, sampling frequency control, and CSV export.
- A software architecture analysis demonstrating the application of MVVM in the context of sensor-driven Android applications.
- An evaluation study assessing the usability and task load of the data collection tool from the perspective of technical users and researchers.

## 2. Related Work

### 2.1 Human Activity Recognition: An Overview

Human Activity Recognition (HAR) has been an active research area for over two decades. Early work relied on dedicated wearable sensors and body-attached inertial measurement units (IMUs) [3]. With the widespread adoption of smartphones, however, attention shifted to using built-in phone sensors as a convenient, unobtrusive alternative [4].

The majority of HAR systems follow a pipeline consisting of: (1) data collection, (2) pre-processing (noise filtering, segmentation into sliding windows), (3) feature extraction (time-domain and frequency-domain statistical features), (4) model training (e.g., SVM, Random Forest, LSTM), and (5) real-time inference [5].

### 2.2 Benchmark Datasets

Several benchmark datasets have shaped HAR research:

- **UCI-HAR (2012)** [1]: Collected from 30 subjects using a Samsung Galaxy S2 (50 Hz), covering six activities (walking, walking upstairs, walking downstairs, sitting, standing, laying). One of the most widely used HAR benchmarks.
- **PAMAP2 (2012)** [2]: Collected from 9 subjects using wrist and ankle IMUs, covering 18 activities. Richer in sensor modalities but requires specialized hardware.
- **WISDM (2019)** [6]: Collected from 51 subjects using Android and iOS devices covering 18 activities including hand-based gestures.
- **MHEALTH (2014)** [7]: A dataset focusing on body sensor networks for health monitoring.

While these datasets are invaluable resources, their fixed nature means they do not cover all possible research scenarios. Researchers studying specific populations (e.g., elderly users, athletes), custom activity taxonomies, or novel devices need to collect their own data.

### 2.3 Existing Data Collection Tools

Several tools have been proposed for mobile sensor data collection:

- **SensorLog** (iOS): A popular iOS app allowing sampling of various sensors and exporting to CSV. However, it is limited to the iOS ecosystem and is not configurable for activity labelling.
- **PhysiLog** [8]: An Android application for ambulatory activity data collection, but with limited activity configuration flexibility and no real-time visualization.
- **AndroSensor**: A general-purpose Android sensor logging app. Primarily targeted at developers, not researcher workflows with labelled activities.
- **AWARE Framework** [9]: A powerful research-grade mobile sensing framework. However, it has a steep setup curve and requires knowledge of its API, making it less suitable for straightforward data collection studies.

In contrast to the above tools, RealTimeHAR is specifically designed for the HAR research workflow: it integrates sensor configuration, activity labelling, subject identification, background recording, and real-time visualization into a unified, usable interface.

### 2.4 MVVM in Android Applications

The Model-View-ViewModel (MVVM) architectural pattern was introduced by Microsoft and later adapted for Android development [10]. In Android, MVVM leverages the `ViewModel` class from the Android Architecture Components library, which survives configuration changes (e.g., screen rotation) and decouples UI state from the UI controller (Activity or Fragment). This separation of concerns improves testability, maintainability, and resilience. The pattern has been widely adopted in modern Android development and is the recommended architecture by Google [11].

### 2.5 Summary and Gap Analysis

The literature review reveals that while HAR is a well-studied field and several data collection tools exist, there remains a need for a purpose-built, researcher-oriented Android tool that combines: configurable multi-sensor selection, flexible activity labelling, background data collection with service-based reliability, real-time signal visualization, and an easy export workflow. This thesis addresses this gap.

## 3. Background and Fundamentals

### 3.1 Smartphone Sensors for HAR

Modern Android smartphones expose a wide range of sensors through the Android `SensorManager` API. The most relevant for HAR are:

| Sensor | Description | Unit |
|---|---|---|
| **Accelerometer** | Measures linear acceleration along X, Y, Z axes, including gravity | m/s² |
| **Gyroscope** | Measures angular rotation rate along X, Y, Z axes | rad/s |
| **Linear Accelerometer** | Accelerometer with gravity removed via software | m/s² |
| **Gravity Sensor** | Direction and magnitude of gravity vector | m/s² |
| **Rotation Vector** | Device orientation relative to the Earth's reference frame | (unit-less quaternion) |
| **Magnetometer** | Measures ambient magnetic field along X, Y, Z axes | μT |
| **Barometer** | Measures atmospheric pressure | hPa |

For HAR tasks such as walking, running, sitting, and standing, the accelerometer and gyroscope are considered the most discriminative sensors [5][12]. Their combination provides both translational (linear motion) and rotational motion data, enabling robust classification.

### 3.2 Sampling Rate Considerations

The Android `SensorManager` allows the application to request a desired sampling period (in microseconds). In RealTimeHAR, the following frequency options are exposed:

| Option | Period | Frequency |
|---|---|---|
| Low | 50,000 µs | 20 Hz |
| Normal | 20,000 µs | 50 Hz |
| High | 10,000 µs | 100 Hz |
| Max (Fastest) | `SENSOR_DELAY_FASTEST` | Device-dependent |

The choice of sampling rate is a trade-off: higher rates capture faster motion details but produce larger files and higher battery consumption. 50 Hz is generally considered sufficient for discriminating typical daily activities [1][5].

### 3.3 Android Platform Architecture

The Android application framework is built around the concept of four core components: Activities, Services, Broadcast Receivers, and Content Providers. For RealTimeHAR:

- **Activity**: `MainActivity` serves as the single-activity host, managing the Fragment back stack.
- **Fragments**: Modular UI screens (DataAcquisition, Configuration, Visualization, Profile).
- **Service**: `KeepAliveService` is a foreground service ensuring sensor listeners remain registered when the app is in the background.
- **SQLite Database**: Provides persistent storage for sensor and activity configurations.

The Android foreground service mechanism is critical for data collection applications. A foreground service runs with higher priority than background services, reduces the probability of being killed by the system under memory pressure, and manifests as a persistent notification visible to the user.

### 3.4 The MVVM Architectural Pattern

MVVM separates the application into three layers:

- **Model**: Plain Old Java Objects (POJOs) and data-access classes (database helpers, file I/O) that define the data and its access rules.
- **View**: Fragments and layouts that render UI and handle user input events.
- **ViewModel**: Mediates between View and Model; holds and exposes UI-relevant state using `LiveData` or plain observable objects; survives configuration changes.

In RealTimeHAR, the ViewModel layer retains the list of configured sensors, the selected activities, sensor readings for charting, and recording state — all of which must survive screen rotation and Fragment transitions.

### 4.4 Data Flow

The end-to-end data flow of RealTimeHAR is as follows:

1. **Configuration Phase**: The researcher opens the Configure screen and:
   - Selects sensors via the `SensorConfigureFragment` (persisted to `SensorDbHelper` / SQLite).
   - Sets the sampling frequency (persisted via `SharedPreferences`).
   - Defines activity labels via the `ActivityConfigureFragment` (persisted to `ActivityDbHelper` / SQLite).
   - Sets a subject identifier (persisted via `SharedPreferences`).

2. **Recording Phase**: On tapping "Start" in `DataAcquisitionFragment`:
   - `KeepAliveService` is started as a foreground service.
   - `SensorManager` registers `SensorEventListener` instances for each selected sensor at the configured frequency.
   - Each sensor event updates a `Map<Sensor, float[]>` holding the latest reading.
   - A `java.util.Timer` fires at the configured period (ms), synchronizes the latest readings across all sensors, and writes one row to the CSV file.
   - Simultaneously, the live chart is updated via the `MPAndroidChart` library.

3. **Export / Review Phase**: On stopping recording:
   - The `FileWriter` is closed and the CSV file is finalized on external storage.
   - The `ProfileFragment` lists all recorded CSV files.
   - A file can be selected to open the `DataVisualizationFragment` for playback visualization.
   - A file can be downloaded to the device's `Downloads` folder or deleted.

### 4.5 CSV Output Format

Each recorded CSV file is named with the pattern: `{ActivityLabel}{yyyyMMdd_HHmmss}.csv`.

The file structure is:

```
Timestamp_ms, Subject_ID, Activity_Label, SENSOR_NAME x, SENSOR_NAME y, SENSOR_NAME z, ...
1695300000000, Subject_01, walking, 0.123, -9.789, 0.456, 0.001, 0.002, -0.003
1695300000020, Subject_01, walking, 0.130, -9.780, 0.460, 0.001, 0.002, -0.003
...
```

This format is directly importable into Python (via `pandas.read_csv()`), MATLAB, or R for downstream machine learning experiments.

### 5.3 Sensor Configuration

The `SensorConfigureFragment` dynamically queries the Android `SensorManager` for all sensors available on the device at runtime:

```java
List<Sensor> sensors = sensorManager.getSensorList(Sensor.TYPE_ALL);
```

Each sensor is rendered as a `CheckBox` in a scrollable `LinearLayout`. Selection state changes are immediately reflected in `SensorConfigureViewModel` (in-memory) and persisted to `SensorDbHelper` (SQLite). This dual persistence ensures that:
- The ViewModel provides the runtime truth during an active recording session.
- The database provides restoration of selections when the app is restarted.

The sampling frequency is exposed as a dropdown (`AutoCompleteTextView`) with four options (20 Hz, 50 Hz, 100 Hz, Max), and the selected value (in microseconds) is stored via `SharedPreferences` for persistence across restarts.

### 5.4 Activity and Subject Configuration

The `ActivityConfigureFragment` presents a `ChipGroup` for managing activity labels. Activities are stored in an SQLite table managed by `ActivityDbHelper`. The subject identifier is a free-text `EditText` field backed by `SharedPreferences`.

Key design decisions:
- **Chip-based activity selection**: Only one activity can be active (selected) at a time during recording; the chip UI provides clear visual feedback of the selected activity.
- **Close icon on chips**: Allows researchers to delete obsolete activity labels.
- **Subject ID persistence**: The subject ID is auto-restored from `SharedPreferences` between sessions, reducing setup friction during multi-session data collection studies.

### 5.5 Data Acquisition and Recording

The `DataAcquisitionFragment` is the core recording screen. When "Start" is pressed:

1. **KeepAliveService** is launched as a foreground service. This creates a persistent system notification ("Real Time HAR running — Sensor data collection ongoing") and elevates the process priority, preventing the Android OS from killing the app under memory pressure.

2. For each selected sensor, a dedicated `SensorEventListener` is registered:
```java
sensorManager.registerListener(listener, sensor, samplingPeriodUs);
```

3. Each `onSensorChanged()` event stores the latest `float[]` values for that sensor in a shared `Map<Sensor, float[]>`:
```java
latestSensorReadings.put(event.sensor, event.values);
```

4. A `java.util.Timer` fires a `TimerTask` at the configured period. The `TimerTask` checks whether all registered sensors have at least one reading available, then calls `writeSensorDataToFile()` to write a synchronized row to the CSV.

This synchronized-write design is a key implementation decision. Android's `SensorManager` delivers events for different sensors at slightly different times, even when the same nominal frequency is requested. Naively writing one CSV row per event would produce unaligned columns. By collecting the latest reading per sensor in a map and writing periodically, the implementation achieves temporal alignment across sensors within the output file.

#### 5.5.1 CSV Writing

The `writeSensorDataToFile()` method writes the CSV header on the first invocation, then appends data rows:

```java
// Header example:
// Timestamp_ms, Subject_ID, Activity_Label, Accelerometer x, Accelerometer y, Accelerometer z, ...

// Data row:
// 1695300001234, Subject_01, walking, 0.123, -9.789, 0.456, ...
```

Files are written to `getExternalFilesDir(null)/RealtimeHAR/` using a `FileWriter` in append mode, making the storage app-specific (no broad external storage permission required above Android 10) while still being accessible via the Files app.

#### 5.5.2 Real-time Visualization

Live sensor charts are rendered using the **MPAndroidChart** library. Each selected sensor gets its own `LineChart` dynamically added to a `LinearLayout` container. Up to three data series (X, Y, Z axes) are plotted per chart using cubic Bezier smoothing (`LineDataSet.Mode.CUBIC_BEZIER`). The chart scrolls to show the last 150 data points, providing a rolling window view of the sensor signal.

### 5.6 File Management

The `ProfileFragment` lists all CSV files in the `RealtimeHAR` app directory using a `RecyclerView`. For each file, the `FileAdapter` exposes three actions via `FileItemClickListener`:

- **Tap (View)**: Opens `DataVisualizationFragment` and plots the file's sensor channels.
- **Download**: Copies the file to the system `Downloads` folder via `MediaStore` API (handles Android 10+ scoped storage) or direct file copy (Android 9 and below).
- **Delete**: Removes the file from storage and refreshes the list.

### 5.7 Post-hoc Data Visualization

`DataVisualizationFragment` reads the selected CSV file line by line (up to 2000 data rows for performance), parses sensor groups from the header, and constructs a `SensorData` model containing a `List<double[]>` per sensor group. It then creates one `LineChart` per sensor group with a separate `LineDataSet` per channel (X, Y, Z axes), each assigned a random color for distinguishability.

### 5.8 Local Persistence via SQLite

Two `SQLiteOpenHelper` subclasses manage local persistence:

**SensorDbHelper**: Stores the names of user-selected sensors.

```sql
CREATE TABLE sensors (id INTEGER PRIMARY KEY AUTOINCREMENT, sensor_name TEXT UNIQUE);
```

**ActivityDbHelper**: Stores activity label definitions and tracks which activity position is currently "active".

```sql
CREATE TABLE activities (id INTEGER PRIMARY KEY AUTOINCREMENT, activity_name TEXT);
CREATE TABLE active_activity (position TEXT);
```

The use of SQLite rather than `SharedPreferences` for these configurations is justified by the need for list semantics (multiple sensors, multiple activities) and the need for individual deletion operations.

### 6.1 Evaluation Overview

The evaluation of RealTimeHAR focuses on two dimensions:
1. **Usability**: Assessed using the System Usability Scale (SUS).
2. **Cognitive and Physical Workload**: Assessed using the NASA Task Load Index (NASA-TLX).

Both instruments were administered to **[N]** participants with a technical background (e.g., computer science students, researchers, or engineers) who were asked to perform a standardized data collection task using the application.

### 6.2 Study Protocol

Participants were asked to:
1. Install the application on their own Android smartphone.
2. Configure the accelerometer and gyroscope sensors at 50 Hz.
3. Define four activity labels: *walking*, *running*, *sitting*, *standing*.
4. Set a subject identifier.
5. Perform each activity for 30 seconds while the app records data in the background (with the screen off during the "background collection" condition).
6. Export and verify the resulting CSV files.

### 6.3 System Usability Scale (SUS)

The SUS is a 10-item Likert-scale questionnaire validated for measuring perceived usability of software systems [13]. Scores range from 0 to 100, with scores above 68 considered "above average" usability, and scores above 80 classified as "Excellent" or Grade A.

**SUS Scoring Formula:**
- Odd questions (1, 3, 5, 7, 9): Score = Response − 1
- Even questions (2, 4, 6, 8, 10): Score = 5 − Response
- Final SUS Score = Sum of all adjusted scores × 2.5

## 7. Discussion

### 7.1 Design Decisions and Justifications

**Synchronized multi-sensor writing via Timer**: The choice to use a periodic `Timer` task rather than writing per-sensor-event ensures temporal alignment across sensors in the output CSV. The trade-off is a potential sub-sample-level jitter introduced by the Timer resolution, but this is negligible for the frequencies used in HAR (20–100 Hz).

**Foreground Service for background collection**: Android's process lifecycle management aggressively terminates background processes under memory pressure. The `KeepAliveService` (`START_STICKY`) combined with a foreground notification is the standard and most reliable mechanism for sustained background data collection. An alternative — WorkManager — is not suitable for continuous, real-time sensor streaming.

**SQLite for configuration persistence**: `SharedPreferences` is designed for key-value pairs, not lists. Using SQLite for sensor and activity configurations provides the required list semantics (add, remove, query) with standard relational operations, at minimal overhead.

**MVVM architecture**: The MVVM pattern's `ViewModel` survives Fragment/Activity recreation (e.g., screen rotation), which is particularly important during a recording session. Without a ViewModel, screen rotation would destroy the Fragment and stop all sensor listeners.

### 7.2 Limitations

1. **Single-activity recording**: Each recording session is tagged with a single activity label. Multi-activity sessions (where the researcher transitions between activities during one file) are not supported. This requires the researcher to start a new recording session per activity.

2. **Timer-based synchronization latency**: The periodic timer writes the *latest* reading of each sensor, not the reading at a precise timestamp. Under high-frequency recording, the effective sampling rate may be slightly lower than configured.

3. **File access compatibility**: The file download mechanism has two code paths (pre- and post-Android 10 scoped storage), adding complexity. Future versions should unify this using the Storage Access Framework.

4. **No real-time ML inference**: The current application does not include a machine learning inference component. It is designed purely as a data collection tool. Real-time activity prediction would require the integration of a TensorFlow Lite model.

5. **Limited to portrait orientation**: The app is locked to portrait mode (`android:screenOrientation="portrait"`). While this prevents accidental layout disruptions during physical activity, it limits usability in landscape contexts.

6. **Samsung-specific permission**: The `com.samsung.permission.SSENSOR` permission is declared for access to higher-rate Samsung sensor APIs. This has no effect on non-Samsung devices but adds a platform-specific dependency.

### 7.3 Threats to Validity

- **Participant sample**: The evaluation study recruited technical participants (researchers, students). Generalizability to non-technical users should not be assumed.
- **Placeholder results**: The evaluation results presented in Chapter 6 are hypothetical. Conclusions drawn from them should be treated as preliminary until real data is collected.
- **Device variability**: Sensor availability, naming conventions, and maximum sampling rates vary significantly across Android device models. The dynamic sensor enumeration approach mitigates this risk.

## 8. Conclusion and Future Work

### 8.1 Conclusion

This thesis presented the design, implementation, and evaluation of **RealTimeHAR**, a configurable Android application for real-time sensor data collection targeting Human Activity Recognition research.

The application successfully addresses the identified gap in the HAR research tooling ecosystem: it provides a flexible, researcher-oriented workflow for configuring sensors, defining activity labels, recording multi-sensor data in the background, visualizing signals in real time, and exporting structured CSV datasets. The implementation follows sound software engineering principles — MVVM architecture, foreground services for reliability, SQLite for configuration persistence — resulting in a maintainable, testable, and extensible codebase.

Preliminary evaluation using the SUS and NASA-TLX instruments suggests that the application achieves good usability (SUS ≈ 76) with a low-to-moderate workload (TLX ≈ 24.5) for technical users, validating the design decisions made during development.

The application collected labelled sensor data for four standard HAR activities — **walking**, **running**, **sitting**, and **standing** — and the exported CSV format is directly compatible with standard machine learning toolchains in Python, R, and MATLAB.

### 8.2 Future Work

Several directions are identified for future development:

1. **Real-time ML Inference**: Integrate a TensorFlow Lite model for on-device activity classification, enabling the application to serve both as a data collection tool and a real-time HAR demo. This would complete the full HAR pipeline within a single app.

2. **Multi-activity session tagging**: Allow the researcher to switch activity labels during a single recording session via a quick-access UI element, annotating transitions in the CSV output.

3. **Cloud synchronization**: Add optional upload of CSV files to cloud storage (e.g., Google Drive, Firebase Storage) for distributed multi-participant studies where files need to be centrally aggregated.

4. **Wearable sensor integration**: Extend the architecture to support Bluetooth-connected wearables (e.g., smartwatches, external IMUs) via the Android Bluetooth LE API, enabling richer sensor modalities.

5. **Cross-platform support**: Investigate a Flutter or React Native port of the application to support iOS data collection with the same toolchain, broadening the diversity of devices from which datasets can be collected.

6. **Automated data quality checks**: Add post-recording validation that reports the actual observed sampling rate, detects gaps or dropouts in the data, and warns the researcher if the quality is below a configured threshold.

7. **Full-scale user study**: Conduct a rigorous, IRB-approved user study with a statistically significant sample size to replace the placeholder evaluation results with real empirical data.
